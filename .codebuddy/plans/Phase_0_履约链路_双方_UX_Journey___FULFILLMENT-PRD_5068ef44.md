## 用户需求

Phase 0 自营试点聚焦履约环节：用户在现有用户端 web app（即 studio 编辑+下单模块，止于支付）完成支付后，用户制作的文件、下单数量、收货地址等信息如何流转到下一环节——自营侧拿到编辑文件去制作，并按信息安排物流或自取。以「1 名自营履约人力 + 用户」为双方主角，先梳理双方 UX journey 供核对，核对通过后再形成需求 PRD。本阶段不改 web 原型、不做界面。

## 产品概述

两份新文档、两处既有文档同步：

1. **履约双方旅程核对稿**：从支付成功讲到用户到手，用户与履约人力两条线并列展开，含系统在中间的数据交接，供用户核对方向；
2. **履约链路 PRD**：核对定稿后产出，规格化用户侧改动与履约侧跑单流程，作为后续开发依据；
3. 既有用户端 PRD 与核心文档的旅程收尾处补交叉引用，保持口径链完整。

## 核心功能

- **三泳道全链路时序**：用户 / 系统 / 履约人力三方的动作与数据交接时序，覆盖「支付成功 → 文件导出 → 落表 → 制作 → 交付 → 状态回传」
- **用户侧 journey**：支付成功 → 制作跟踪 → 取货（自提码）或收货（快递跟踪）→ 售后取消，与核心文档用户旅程 #12 衔接续编
- **履约侧 journey**：1 名人力的 SOP 级动作流——接单、拼版、打印、模切、品检、包装、交付，每步含工具与异常出口
- **时效承诺分层**：自提当日取（默认）+ 同城普通快递次日达兜底 + 现场单变体；闪送不进本期，留人工个案通道——把「自提布点少 vs 快递不够快」的张力结构化为分层方案，由数据验证
- **异常流**：设备故障、品质不合格、超时未取、取消退款、客诉的处理路径
- **UE 记账采集点**：耗材成本、人力分钟数、配送费、客诉在流程各步的记录位置
- **现场单变体**：漫展/快闪「当场下单当场拿」的流程分支

## 视觉效果

纯文档交付：泳道时序图、状态机图、对照表格与要点列表，行文风格与现有战略文档一致（要点表格化、口径可回溯），无界面产出。

## 技术栈选择

- **载体**：Markdown 文档置于 `documents/`，与 SOD.md / PRD.md / PLATFORM.md / BRIEF.md 同级
- **图表**：Mermaid（sequenceDiagram 三泳道时序、stateDiagram-v2 状态机、flowchart 分层流程）——PRD.md §2.3 / §4.10 / §5.1-5.2 已有成熟用法，沿用惯例，GitHub 渲染直接可读
- **行文纪律**：对齐 PLATFORM.md v2.1a 风格——要点表格化、口径引用不复制、章节号回溯标注；术语复用 PRD.md §1.3 术语表（结算袋/安全区/模切轮廓），不引入新名词

## 实现方案

### 交付节奏（用户已拍板）

journey 核对稿先行 → 用户 checkpoint → 按反馈定稿 → 履约 PRD → 交叉引用同步 → commit 信息。沿用 BRIEF.md「文稿先行核对」节奏，避免方向偏差导致 PRD 返工。

### 时效承诺分层（对用户犹豫的结构化回答，journey 稿中作为建议方案呈现，核对时用户可推翻）

不二选一，把张力转为三层结构：

- **自提（默认推荐）**：自营节点（办公场地一角）当日取，设截单时间 SLA（如 18:00 前下单当日可取，具体时刻列入 journey 开放问题）
- **同城普通快递**：次日达兜底，N=1 运费 5 元模型沿用（引 SOD.md 计价章）——覆盖自提半径外用户；次日达 vs 竞品 3-7 天仍是 2-3 倍快
- **现场单变体**：漫展/快闪当场下单当场拿——「快」的终极展示
- **闪送不进本期**：留人工客服个案通道收集需求信号，验证后再议系统化

「单点自提会否劝退用户」不靠猜：下单确认页配送方式并列呈现、用户自选，Gate 0「自提占比 ≥40%」实测回答；「当日达兑现率 ≥80%」分母锁定自提线，口径可算。

### 核心数据流（回答「文件+数量+地址怎么到下一环节」）

支付回调触发最小后端管道，无界面、只做四件事：

1. **导出打印文件**：编辑器画布 → 打印文件（每作品一份，与订单行关联），存对象存储；拼版发生在文件层（PLATFORM.md §8.0 整单派发原则：拼版≠拆单）
2. **写入飞书多维表格**：订单行含订单号、用户、作品数、总张数 N、配送方式（自提/快递）、地址/自提点、实付、UE 记账字段（耗材成本、人力分钟数、配送费、客诉）——PLATFORM.md §8.1 W1-2「跑单表格字段定版」的落地
3. **状态回传**：履约人力在表格推进状态（拼版→打印→待取/已发快递）→ 管道同步回用户端订单详情（轮询或手动触发，Phase 0 从简）
4. **物流单号回填**：快递发货后人工在表格回填，管道同步用户端物流页

打印文件命名规范：`订单号-作品序号-份数`，自提与快递共享同一制作 SOP，仅交付段分叉。

### 文档结构设计

**documents/FULFILLMENT-JOURNEY.md（核对稿，先行）**

1. 文档说明与读法（对照 SOD.md 旅程 #0-12，本文从 #11 支付成功续起）
2. 全链路三泳道时序图（用户/系统/履约人力）
3. 用户侧 journey 表：阶段/用户动作/所见/情绪关注点——支付成功页→制作中→取货通知（自提码）/快递单号→到手→售后
4. 履约侧 journey 表（1 人力 SOP 级）：新单提醒→接单确认→拼版导出→打印→模切→品检→包装→自提上架/快递交发→状态回传→UE 记账——每步含工具（飞书表格/S1/包装台）、耗时预估位、异常出口
5. 时效承诺分层矩阵：形态/承诺话术/成本/适用人群/验证指标
6. 异常流五条：设备故障、品质不合格、超时未取、取消退款、客诉
7. 现场单变体：漫展/快闪当场拿的简化流程（现场设备、现场交付、免运费）
8. 开放问题清单（核对重点）：截单时刻、自提营业时间、超时未取保留天数、快递超区处理

**documents/FULFILLMENT-PRD.md（定稿后）**

1. 文档说明：范围（支付后→到手）、与 PRD.md 边界（用户端交互归 PRD.md，本文只含因履约新增的用户侧改动：checkout 配送方式区、取货码、订单状态扩展）、角色定义（用户/履约人力/最小后端管道）
2. 系统拓扑：web app / 最小后端管道 / 飞书表格 / S1 设备，Phase 0 不建后台界面（PLATFORM.md §8.0 自研 vs 购买原则：验证阶段两个都不建）
3. 用户侧规格：checkout 配送方式选择（自提/快递并列、运费规则联动）、订单状态机 v2（现四态扩展为双线：自提线 含「待自提/已完成」、快递线含「已发货」）、取货码生成与展示、通知触点（短信/企微，Phase 0 从简）
4. 履约侧规格：飞书表格 schema（字段名/类型/枚举值/UE 记账字段）、跑单 SOP（对应 journey 履约侧表格）、截单与交付 SLA、异常 SOP
5. 系统接缝规格：支付回调→文件导出→落表→状态回传的最小管道（无界面）、数据流向图
6. 待定项：依赖 S1 的打印文件规格细节、快递服务商选择、通知渠道、状态同步频率
7. 不做项：闪送系统化、挂机店自提、商家端、多节点派单

### 关键决策

- **新独立文档而非扩 PRD.md**：PRD.md §1.1 已声明不含履约侧，边界即纪律；履约 PRD 独立成文，用户侧改动以「增量规格」形式写并在 PRD.md 补交叉引用
- **最小后端管道而非人工搬运**：支付回调落表与文件导出若靠人工（登录服务器下载、复制粘贴），1 人力会被文件搬运吞掉且易错；管道只做四件事、无界面，符合「验证阶段不建系统」精神，又是跑单前必需的地基
- **状态回传从简（轮询/手动）**：Phase 0 不做实时推送，避免过度工程；表格→代码切换信号（日均单量 >30）触发时再升级
- **自提码用简单生成规则**（订单号派生），不引入专门取件系统——1 节点 1 人力，人工核码即可

### 性能与可靠性

- 时效承诺的核心约束是截单时间：打印+模切+品检+包装的单均人力分钟数是 SLA 的硬约束，journey 履约侧表格中每步留耗时预估位，Gate 0 前 W1-2 用真实订单校准——这正是 UE 账本「人力分钟数」字段的采集目的
- 异常出口全覆盖：每个履约步骤定义失败时的用户侧话术与补偿动作（如打印失败→「制作中」不推进+主动通知），避免用户面对无解释的等待
- UE 记账字段在表格落字段级（耗材成本/人力分钟/配送费/客诉），W11-12 Gate 0 数据汇总直接从表格出，零二次加工
