## 二、当前线上架构（一张图记全）

```
观众手机（流量扫码）──┐
                     ├─→ GitHub Pages 静态页（booth/console/m/index.html）
摊位屏（投影）───────┤         │
                     │         ↓ REST + Realtime（WebSocket）
运营控制台（你的电脑）─┘   Supabase Postgres（5 张 demo_ 表 + 8 个 RPC + RLS）
```

**核心机制**：anon key 只读（RLS `read` 策略），所有写操作走 `SECURITY DEFINER` RPC——发号、状态机推进、核码规则不可被前端绕过。打印仿真由浏览器端泵循环驱动（任一工作人员页面开着，每 2.5s 调一次幂等的 `demo_pump()`），无服务器进程。

## 四、踩坑全记录（按遇到顺序，含解法）

| 坑 | 现象 | 解法 |
|---|---|---|
| **SQL Editor 破坏性警告** | 粘贴 schema 弹红色警告「destructive operations / UPDATE without WHERE」 | 那是提示不是报错，确认执行即可——清场逻辑本来就是设计意图 |
| **42710 重复订阅** | `relation already member of publication supabase_realtime`（重复执行 schema 时中断） | Realtime 订阅改为 DO 块逐表条件添加（先查 `pg_publication_tables` 再决定是否 add） |
| **RLS 策略重复创建** | 同上场景下重跑可能报策略已存在 | 五条 read 策略改为先 `drop policy if exists` 再 create |
| **safeupdate 扩展拦截**（最隐蔽） | RPC 调用报 `21000: DELETE requires a WHERE clause`——项目开了 safeupdate，函数体内整表 DELETE/UPDATE 也拦截 | 全表清场语句补 `where true`（语义不变，safeupdate 放行） |
| **PowerShell JSON 转义** | curl 传 body 报 `PGRST102 Empty or invalid json` | 用 `[IO.File]::WriteAllText` 写无 BOM UTF-8 临时文件 + `--data-binary "@file"` |
| **.gitignore 挡住 config.js** | Pages 只渲染 git 内文件，忽略 config.js 会导致线上 404 | 移出 .gitignore 入库——anon key 本就是可公开的前端凭证（RLS 只读+RPC 白名单防护） |

**教训沉淀**：SQL Editor 里 success ≠ 部署可用。schema 改动后必须**用 anon key 走一遍真实 RPC 调用**（本次 safeupdate 问题纯 SQL Editor 完全测不出来）。
